# 24 — Time, Lifecycle & Temporal Modeling Architecture

## 1. Purpose

Time is a first-class dimension of the ShopSphere synthetic e-commerce world.

The generator should not merely attach random timestamps to records.

Temporal values should describe a coherent business world in which:

- customers are acquired at meaningful times;
- sessions occur during customer activity periods;
- events occur within sessions;
- orders occur as consequences of customer activity;
- payments occur around order creation;
- shipments occur after orders and payments according to business rules;
- returns occur after eligible fulfillment events;
- products and promotions can have temporal availability;
- demand can vary by hour, day, week, season, campaign, and lifecycle;
- customer behavior can evolve over time.

The goal is **temporal coherence**, not simply timestamp validity.

---

# 2. Core Principle

A timestamp is useful only when its relationship to other timestamps makes business sense.

Bad temporal generation:

```text
customer.created_at = random date
order.created_at    = random date
shipment.created_at = random date
return.created_at   = random date
```

Every value may individually be valid.

The dataset is nevertheless temporally incoherent.

Preferred generation:

```text
customer acquisition
        ↓
customer activity
        ↓
session
        ↓
events
        ↓
order
        ↓
payment
        ↓
shipment
        ↓
delivery
        ↓
return eligibility
        ↓
return
        ↓
refund
```

Each stage constrains the next.

---

# 3. Temporal Architecture Goals

The temporal architecture should provide:

1. reproducibility;
2. valid timestamp ranges;
3. entity lifecycle coherence;
4. event ordering;
5. realistic durations;
6. customer lifecycle behavior;
7. seasonality;
8. campaign effects;
9. configurable time windows;
10. temporal skew;
11. deterministic generation;
12. efficient large-scale generation.

---

# 4. Time Has Multiple Meanings

ShopSphere should distinguish at least three concepts:

```text
event time
business time
generation time
```

## Event time

When something happened in the simulated business world.

## Business time

The effective period during which a business rule applies.

Examples:

```text
promotion valid_from → valid_to
product available_from → available_to
return window
```

## Generation time

When the synthetic record was actually generated by the program.

These concepts should not be conflated.

---

# 5. Event Time

Most generated timestamps should represent simulated event time.

Examples:

```text
customer registration
session start
product view
order creation
payment
shipment
delivery
return
```

This is the primary temporal axis of the dataset.

---

# 6. Generation Time

The generator may run on:

```text
2026-09-15
```

while generating a historical dataset for:

```text
2024-01-01 → 2025-12-31
```

Therefore:

```text
generated_at
```

should not automatically become:

```text
event_timestamp
```

The simulated timeline should be controlled by configuration.

---

# 7. Dataset Time Window

The generator should eventually support an explicit dataset window:

```text
start = 2024-01-01T00:00:00
end   = 2025-12-31T23:59:59
```

All applicable business events should fall within the requested simulation horizon.

Some lifecycle records may have semantics that begin before the main window, but such behavior must be explicit.

---

# 8. Time Configuration

A conceptual configuration:

```hocon
time {
  start = "2024-01-01T00:00:00"
  end = "2025-12-31T23:59:59"

  timezone = "Asia/Kolkata"

  seasonality {
    enabled = true
  }

  campaigns {
    enabled = true
  }
}
```

The exact configuration structure can evolve.

The important principle is centralized temporal policy.

---

# 9. Time Zone

Time zone must be explicit.

For an India-centric ShopSphere scenario:

```text
Asia/Kolkata
```

may be the baseline.

A future global scenario may support multiple customer-local time zones.

Do not silently mix:

```text
UTC
local business time
JVM default timezone
```

---

# 10. UTC vs Local Time

A robust design should distinguish:

```text
Instant
```

from:

```text
LocalDateTime
```

Use an absolute instant where ordering across systems matters.

Use local date/time where business behavior depends on local clock time.

Examples:

```text
event ordering → Instant
hour-of-day shopping behavior → ZonedDateTime / local business time
```

---

# 11. Central Time Abstraction

Domain generators should not repeatedly implement:

```scala
random timestamp between start and end
```

A shared temporal component should provide business-level operations.

Conceptually:

```scala
timeModel.randomEventTime(...)
timeModel.sampleDuration(...)
timeModel.nextTimeAfter(...)
timeModel.isWithin(...)
```

The domain should express intent rather than timestamp arithmetic.

---

# 12. Time Model Responsibilities

The time model should own:

- dataset time window;
- timezone;
- temporal distributions;
- business calendars;
- seasonality;
- campaign periods;
- duration sampling;
- ordering constraints.

It should not own:

- customer identity;
- product selection;
- payment method selection.

Those remain domain responsibilities.

---

# 13. Strategy Pattern for Temporal Behavior

Different temporal behaviors are legitimate Strategy candidates.

Examples:

```text
CustomerActivityTimeModel
OrderArrivalModel
SessionDurationModel
EventInterArrivalModel
ShipmentDelayModel
ReturnDelayModel
```

Each can vary independently.

This is preferable to one giant:

```text
TimeManager
```

with dozens of unrelated methods.

---

# 14. Distribution Engine Integration

Temporal behavior should use the shared distribution architecture.

Examples:

```text
normal distribution
log-normal duration
exponential inter-arrival
Poisson arrivals
negative binomial counts
piecewise seasonal rate
mixture distribution
```

The temporal layer defines business meaning.

The distribution layer performs generic sampling.

---

# 15. Temporal Randomness

Time sampling must use deterministic random streams.

Example:

```text
customer.activity-time
order.arrival-time
session.duration
event.inter-arrival
shipment.delay
return.delay
```

Separate semantic streams reduce accidental coupling.

---

# 16. Temporal Reproducibility

Given:

```text
same seed
same configuration
same reference data
same implementation version
```

the temporal sequence should be reproducible.

This is particularly important for benchmark datasets.

---

# 17. Entity Lifecycle

Every temporal entity should have a lifecycle model where appropriate.

Examples:

### Customer

```text
prospect
→ acquired
→ registered
→ active
→ dormant
→ reactivated
→ churned
```

### Order

```text
PLACED
→ CONFIRMED
→ SHIPPED
→ DELIVERED
```

with cancellation paths.

### Shipment

```text
CREATED
→ PICKED_UP
→ IN_TRANSIT
→ OUT_FOR_DELIVERY
→ DELIVERED
```

### Return

```text
REQUESTED
→ APPROVED
→ RECEIVED
→ REFUNDED
```

The exact states depend on each domain document.

---

# 18. Lifecycle vs Status

A status is usually a current state.

A lifecycle is the sequence of states and transitions over time.

This distinction matters.

For example:

```text
order.status = DELIVERED
```

does not by itself tell us:

```text
when placed
when confirmed
when shipped
when delivered
```

A realistic generator may eventually need both:

```text
current status
```

and:

```text
state transition timestamps
```

where the schema supports them.

---

# 19. Current Schema Constraint

The current project models some entities with a relatively compact schema.

Therefore, temporal realism must not be invented as additional output columns merely because they would be useful.

The architecture can define future temporal concepts without changing the current model until the schema is intentionally extended.

This is especially important for maintaining compatibility with the existing project.

---

# 20. Customer Acquisition Time

A customer should have an acquisition or registration time.

Conceptually:

```text
customer.created_at
```

defines when the customer enters the simulated world.

Subsequent activity should normally satisfy:

```text
session.start >= customer.created_at
order.created_at >= customer.created_at
```

---

# 21. Customer Activity Window

A customer should not necessarily be active throughout the entire dataset.

Possible lifecycle:

```text
acquisition
    ↓
high activity
    ↓
reduced activity
    ↓
dormancy
    ↓
reactivation
```

This creates realistic temporal heterogeneity.

---

# 22. Customer Age in System

Behavior can depend on:

```text
days_since_acquisition
```

For example:

```text
new customer
→ exploratory sessions

established customer
→ repeat purchases

dormant customer
→ low activity

reactivated customer
→ temporary campaign-driven spike
```

This should eventually feed CustomerBehaviorProfile.

---

# 23. Customer Lifecycle as Latent State

The CustomerBehaviorProfile can include:

```text
acquisition_time
activity_propensity
purchase_frequency
spending_propensity
return_propensity
price_sensitivity
lifecycle_state
```

These latent variables can drive downstream temporal behavior.

---

# 24. Session Timing

Sessions should be distributed across customer activity rather than uniformly across the entire dataset.

Important dimensions include:

```text
hour of day
day of week
customer lifecycle
campaign periods
seasonality
device/channel
```

---

# 25. Hour-of-Day Behavior

An e-commerce site may have higher activity during certain local hours.

Instead of:

```text
uniform 00:00–23:59
```

use a configurable distribution.

Conceptually:

```text
night       → low
morning     → medium
afternoon   → medium
evening     → high
late night  → declining
```

The exact curve should be configurable rather than hard-coded.

---

# 26. Day-of-Week Behavior

Traffic may differ between:

```text
weekday
weekend
```

Again, this should be modeled as a distribution.

Example:

```text
Monday      0.11
Tuesday     0.12
Wednesday   0.13
Thursday    0.14
Friday      0.16
Saturday    0.17
Sunday      0.17
```

These numbers are illustrative only.

The architecture should not assume these exact values.

---

# 27. Seasonality

Seasonality represents systematic changes across longer time periods.

Examples:

```text
festival season
holiday season
summer
winter
back-to-school
year-end
```

Seasonality can influence:

- traffic;
- category demand;
- product popularity;
- order frequency;
- basket size;
- discounts;
- return behavior.

---

# 28. Campaigns

Campaigns are explicit business events.

Examples:

```text
campaign_start
campaign_end
campaign_type
affected_categories
affected_products
traffic_multiplier
conversion_multiplier
discount_multiplier
```

Campaigns should be modeled as temporal windows.

---

# 29. Campaign Overlap

Multiple campaigns may overlap.

The architecture should define whether effects are:

```text
additive
multiplicative
priority-based
mutually exclusive
```

Do not leave this ambiguous.

A campaign engine should eventually resolve an effective temporal context.

---

# 30. Temporal Context

A useful conceptual object is:

```text
TemporalContext
  timestamp
  localDate
  dayOfWeek
  hour
  season
  campaigns
  lifecycle
```

Domain behavior can consume this context.

This reduces repeated calculations.

---

# 31. Time and Product Demand

Product popularity should not necessarily be static.

A product can have:

```text
baseline popularity
+
category seasonality
+
brand effects
+
campaign effects
+
product lifecycle
```

This creates time-varying demand.

---

# 32. Product Lifecycle

A product may move through:

```text
planned
→ launched
→ active
→ declining
→ discontinued
```

The current Product model may not expose all these states.

The generator can nevertheless use internal lifecycle state to influence generation where appropriate.

---

# 33. Availability Constraint

If future product lifecycle is modeled:

```text
order item timestamp >= product.available_from
```

and:

```text
order item timestamp <= product.discontinued_at
```

where those boundaries exist.

A product should not receive purchases before launch unless the scenario explicitly models pre-launch activity.

---

# 34. Order Time

Order time should emerge from customer activity and conversion behavior.

The preferred conceptual flow is:

```text
customer behavior
        ↓
session activity
        ↓
purchase intent
        ↓
conversion
        ↓
order timestamp
```

This is stronger than independently generating order timestamps.

---

# 35. Order Arrival Process

At larger scale, order generation can be modeled as an arrival process.

Potential models:

```text
Poisson
non-homogeneous Poisson
negative binomial
piecewise rate
mixture
```

For realistic e-commerce data, a non-homogeneous process is often more expressive:

```text
λ(t)
```

varies with:

```text
hour
day
season
campaign
```

---

# 36. Customer-Driven vs Global Order Generation

Two valid approaches exist.

### Customer-driven

```text
customer
→ number of purchases
→ purchase timestamps
```

Best for behavioral realism.

### Global arrival-driven

```text
time period
→ number of orders
→ customers assigned to orders
```

Best for controlling aggregate temporal traffic.

The target architecture may combine both through calibrated constraints.

---

# 37. Hybrid Temporal Generation

A sophisticated approach:

```text
global temporal demand curve
        ↓
expected order volume by time bucket
        ↓
customer activity allocation
        ↓
customer-specific purchase propensity
        ↓
actual order timestamps
```

This allows both:

```text
global seasonality
```

and:

```text
customer heterogeneity
```

to coexist.

---

# 38. Session-to-Order Temporal Relationship

If an order is attributed to a session:

```text
order.created_at >= session.start
```

and:

```text
order.created_at <= session.end
```

for same-session conversion.

If delayed conversion is modeled, the relationship should instead be explicitly defined.

Do not accidentally imply same-session conversion if the schema/business model does not support it.

---

# 39. Event Ordering

Events within a session should be ordered.

Example:

```text
SESSION_START
PRODUCT_VIEW
PRODUCT_VIEW
ADD_TO_CART
CHECKOUT_START
PAYMENT
ORDER_COMPLETED
SESSION_END
```

The generator should avoid impossible sequences such as:

```text
ORDER_COMPLETED
→ PRODUCT_VIEW
```

unless the event model explicitly permits such behavior.

---

# 40. Event Inter-Arrival Times

Events should not all occur at:

```text
session.start + fixed interval
```

Use configurable duration/inter-arrival distributions.

Potential distributions:

```text
exponential
log-normal
gamma
mixture
```

This produces more realistic timing.

---

# 41. Session Duration

Session duration should correlate with:

```text
event count
intent
customer behavior
device
journey type
```

A browsing session may be longer than a quick repeat-purchase session.

This is a strong example of why independent random timestamps are insufficient.

---

# 42. Event Count and Duration

A useful relationship:

```text
more events
→ generally longer session
```

but with variation.

Avoid:

```text
events = duration / constant
```

because real behavior has substantial dispersion.

---

# 43. Payment Timing

Payment generally follows order creation.

Conceptually:

```text
order.created_at
≤ payment.created_at
```

The exact relationship depends on business semantics.

For immediate payment:

```text
delay ≈ seconds/minutes
```

For delayed payment:

```text
delay may be longer
```

The payment model should own this policy.

---

# 44. Shipment Timing

Shipment should generally occur after:

```text
order placement/confirmation
```

and, where required:

```text
successful payment
```

A conceptual ordering:

```text
order
→ payment
→ shipment
→ delivery
```

The actual state transitions should follow the Shipment domain rules.

---

# 45. Shipment Delay

Delivery time should not be constant.

Factors may include:

```text
origin geography
destination geography
carrier
service level
distance
season
campaign volume
operational incidents
```

Potential distribution:

```text
base delivery duration
+ geography adjustment
+ service-level adjustment
+ seasonal adjustment
+ random variation
```

---

# 46. Shipment SLA

A future shipment model may define:

```text
promised_delivery_time
actual_delivery_time
```

Then:

```text
late = actual > promised
```

Late delivery can become a realistic downstream feature.

---

# 47. Returns

Returns must respect temporal eligibility.

Conceptually:

```text
return.requested_at >= delivery_at
```

and:

```text
return.requested_at <= delivery_at + return_window
```

unless business rules explicitly permit another path.

---

# 48. Return Timing Distribution

Return delays should have variation.

Example conceptual shape:

```text
most returns → shortly after delivery
some returns  → near end of window
few returns   → exceptional long delays
```

A simple uniform distribution is unlikely to capture this well.

---

# 49. Refund Timing

If refund timing is represented:

```text
return.approved
→ refund initiated
→ refund completed
```

with a configurable processing delay.

This can later support payment/refund performance workloads.

---

# 50. Temporal Dependencies

The domain dependency graph is therefore:

```text
Customer acquisition
       ↓
Customer activity
       ↓
Session
       ↓
Event sequence
       ↓
Order
       ↓
Payment
       ↓
Shipment
       ↓
Delivery
       ↓
Return
```

Product lifecycle and campaign context intersect this graph.

---

# 51. Temporal Invariants

Useful invariants include:

```text
session.start >= customer.created_at
```

```text
event.timestamp >= session.start
```

```text
event.timestamp <= session.end
```

```text
order.timestamp >= customer.created_at
```

```text
payment.timestamp >= order.timestamp
```

```text
shipment.timestamp >= order.timestamp
```

```text
return.timestamp >= delivery.timestamp
```

where the corresponding timestamps exist.

---

# 52. Clock Consistency

All temporal comparisons must use compatible time representations.

Avoid comparing:

```text
UTC Instant
```

with:

```text
local timestamp interpreted in another timezone
```

without explicit conversion.

---

# 53. Temporal Validation

Temporal validation should be a dedicated validation layer.

It should check:

- range validity;
- ordering;
- lifecycle consistency;
- timezone consistency;
- duration constraints;
- eligibility windows;
- temporal relationships.

This extends the existing validation architecture.

---

# 54. Temporal Validation Examples

Invalid:

```text
event.timestamp < session.start
```

Invalid:

```text
return.timestamp < shipment.delivery
```

Invalid:

```text
order.timestamp < customer.created_at
```

Invalid:

```text
product.purchase < product.available_from
```

when product availability is modeled.

---

# 55. Temporal Data Quality Scenarios

Dirty-data scenarios can intentionally introduce:

```text
timestamp drift
out-of-order event
invalid timezone
future timestamp
return outside window
```

These should be generated intentionally and validated as expected violations.

---

# 56. Timestamp Corruption

A controlled quality scenario might apply:

```text
timestamp_shift = ±N minutes
```

or:

```text
timestamp_shift = ±N days
```

to a configurable fraction of records.

The corruption engine should remain separate from the clean temporal model.

---

# 57. Temporal Skew

Temporal skew is a legitimate benchmark dimension.

Examples:

```text
festival spike
campaign spike
flash sale
traffic burst
```

This can create:

```text
hot time buckets
```

which are useful for Spark partitioning and aggregation experiments.

---

# 58. Business Skew vs Artificial Skew

A campaign spike is business-realistic.

An artificial benchmark spike may deliberately force:

```text
90% of records into one hour
```

Both can be useful.

The scenario architecture must identify which kind of skew is being requested.

---

# 59. Temporal Partitioning

The generator should eventually make temporal distributions useful for storage.

For example:

```text
year
month
day
```

or:

```text
event_date
```

can support downstream Spark partitioning experiments.

The generator should not hard-code Spark-specific partitioning into domain generation.

---

# 60. Spark Implication

Temporal realism enables later workloads such as:

```text
daily order aggregation
monthly revenue
rolling seven-day metrics
customer activity windows
event-session windows
seasonal comparison
campaign attribution
```

This is one reason temporal architecture matters for the future Spark Performance Laboratory.

---

# 61. Window Functions

Realistic timestamps enable meaningful Spark window workloads:

```text
customer purchase sequence
previous order
next order
time between purchases
session event ordering
```

Without coherent time, these workloads become synthetic in the wrong way.

---

# 62. Watermarks and Event-Time Processing

If streaming experiments are added later, event time can support:

```text
watermarks
late events
out-of-order events
windowed aggregation
```

This is future capability.

The current generator does not need a streaming engine to model event-time semantics.

---

# 63. Late Events

A future scenario may intentionally generate:

```text
event generated late
```

where:

```text
event timestamp < ingestion timestamp
```

This is useful for streaming benchmarks.

Again, this requires explicit schema semantics before implementation.

---

# 64. Business Calendars

Some temporal behavior may depend on:

```text
working days
weekends
holidays
festival periods
```

A business-calendar abstraction may eventually provide:

```scala
isWeekend(date)
isHoliday(date)
season(date)
campaignsAt(timestamp)
```

This should remain separate from generic date arithmetic.

---

# 65. Holiday Modeling

Holiday effects can influence:

```text
traffic
order volume
delivery time
support activity
returns
```

The effect should be configurable.

Do not assume every holiday has the same effect.

---

# 66. Geography and Time

Geography may eventually influence timezone.

Current geography is primarily an address/reference hierarchy.

Future global geography may add:

```text
timezone
regional calendar
local holidays
```

Do not add these to the current Address model.

They belong to geography/reference context.

---

# 67. Customer Local Time

For a global scenario:

```text
customer geography
→ customer timezone
→ local activity time
```

This is preferable to randomly assigning activity hours independent of geography.

---

# 68. Temporal Correlation

Time should influence multiple domains through shared context.

For example:

```text
campaign active
        ↓
traffic ↑
        ↓
sessions ↑
        ↓
events ↑
        ↓
orders ↑
        ↓
shipment load ↑
        ↓
delivery delay ↑
        ↓
returns potentially ↑
```

This creates a coherent causal chain.

---

# 69. Avoiding Independent Multipliers

Do not simply multiply each entity independently:

```text
orders × 2
sessions × 2
events × 2
shipments × 2
```

during a campaign.

That produces correlated counts without modeling why they changed.

Prefer:

```text
campaign context
→ behavior change
→ downstream effects
```

---

# 70. Temporal Behavior and Customer Profiles

CustomerBehaviorProfile should eventually include time-sensitive parameters.

Examples:

```text
baseline activity rate
purchase rate
preferred hours
preferred weekdays
campaign responsiveness
seasonality sensitivity
```

This creates heterogeneous customers.

---

# 71. Temporal Behavior and Product Profiles

Product popularity may include:

```text
baseline demand
seasonal sensitivity
campaign responsiveness
lifecycle stage
```

Therefore:

```text
ProductPopularityModel
```

can consume temporal context.

---

# 72. Temporal Behavior and Returns

Return probability may depend on:

```text
delivery delay
season
product lifecycle
campaign promotion
customer return propensity
```

This is a cross-domain behavioral relationship.

---

# 73. Temporal Behavior and Payment

Payment method usage may vary with:

```text
customer lifecycle
time
campaign
device
```

For example, a customer may behave differently on mobile during a campaign.

These relationships belong in behavior strategies, not in a generic time utility.

---

# 74. Temporal Composition

A clean conceptual design:

```text
TemporalModel
    |
    +-- DatasetClock
    +-- CalendarModel
    +-- SeasonalityModel
    +-- CampaignModel
    +-- DurationModel
    +-- ArrivalModel
```

Not every project implementation needs all these classes immediately.

They are logical responsibilities.

---

# 75. Dataset Clock

The generator should have a single conceptual source of simulation time.

For deterministic batch generation:

```text
DatasetClock
```

provides:

```text
start
end
timezone
```

The system should not scatter calls to:

```scala
Instant.now()
```

through domain generation.

---

# 76. Avoiding Wall-Clock Dependence

A reproducible generator should not make business decisions based on the machine's current time.

Bad:

```scala
if (Instant.now().isBefore(...))
```

Better:

```text
simulation clock
```

controlled by configuration.

---

# 77. Current Implementation

The current project already has generation components that create timestamps and uses deterministic random infrastructure.

However, the temporal architecture is not yet a unified domain-level time model.

Current behavior should therefore be treated as a baseline to refactor rather than assuming the complete temporal architecture already exists.

---

# 78. Migration Strategy

Temporal refactoring should proceed incrementally.

### Step 1

Identify all timestamp generation.

### Step 2

Classify timestamps by business meaning.

### Step 3

Centralize dataset time window.

### Step 4

Introduce shared time abstractions.

### Step 5

Introduce temporal distributions.

### Step 6

Connect lifecycle constraints.

### Step 7

Connect session/event timing.

### Step 8

Connect order/payment/shipment/return timing.

### Step 9

Add seasonality.

### Step 10

Add campaign context.

### Step 11

Add customer lifecycle.

### Step 12

Add temporal statistical validation.

---

# 79. Refactoring Rule

Do not start by creating a giant:

```text
TemporalManager
```

and moving every timestamp into it.

First identify business responsibilities.

Then create focused components.

---

# 80. Readability Rule

Good code should communicate:

```scala
val sessionStart =
  activityModel.sampleSessionStart(
    customer = customer,
    temporalContext = context
  )
```

rather than:

```scala
val ts =
  timeManager.generate(
    random,
    a,
    b,
    mode,
    x,
    y
  )
```

The first communicates business intent.

---

# 81. Strategy Selection

Configuration may select:

```text
uniform session timing
weighted hourly timing
seasonal timing
campaign-aware timing
```

A Factory may construct the selected strategy.

The generator should depend on the behavior contract rather than configuration parsing details.

---

# 82. Dependency Injection

Temporal strategies should receive their dependencies through constructors or method parameters.

For example:

```scala
final class CampaignAwareOrderArrivalModel(
  calendar: BusinessCalendar,
  campaigns: CampaignReferenceData,
  random: RandomGenerator
)
```

No global mutable clock.

---

# 83. SOLID

## Single Responsibility

`SessionDurationModel` should not determine product popularity.

## Open/Closed

New temporal models should be addable without rewriting every entity generator.

## Liskov Substitution

Alternative timing models must satisfy the same semantic contract.

## Interface Segregation

Avoid a giant `TemporalService` interface.

## Dependency Inversion

Domain behavior should depend on focused temporal abstractions where variation is real.

# 93. Benchmark Importance

Two datasets with identical row counts can produce very different Spark behavior if their temporal distributions differ.

Example:

```text
Dataset A:

Dataset B:

```

The second can create different:

```text

window workloads
aggregation patterns
```

Therefore temporal characteristics should be part of dataset identity.

# 94. Performance Considerations

Temporal generation must scale.

Avoid expensive per-record operations such as:

```text
recomputing campaign calendars
rebuilding date structures
sorting all timestamps
```

for every record.

Precompute immutable reference structures where possible.

# 95. Bucket-Based Generation

For large datasets, one efficient approach is:

```text
dataset window
    ↓
time buckets
    ↓
expected volume per bucket
    ↓
generate records within bucket
```

Possible bucket:

```text

```

# 96. Parallel Generation

Parallel generation must preserve deterministic behavior.

Do not use one shared mutable random generator across threads.

Prefer:

```text
root seed
→ entity stream
→ partition/bucket stream
→ record stream
```

This is consistent with the reproducibility architecture.

---

# 97. Ordering and Parallelism

Parallel generation may produce records in a different physical order.

Therefore distinguish:

```text
logical temporal correctness
```

from:

```text
file record order
```

The former is required.

The latter should only be required if the output contract explicitly demands it.

---

# 98. Event Ordering Within a Session

Event ordering is usually a stronger requirement.

Even if records are generated in parallel, event timestamps for one session should preserve:

```text
event_1 <= event_2 <= event_3
```

or whatever ordering contract the event model defines.

# 106. Explicit Architecture Decisions

### Decision 1

Time is a first-class business dimension, not merely a utility concern.

### Decision 2

Simulated event time must be independent of generator wall-clock time.

### Decision 3

Timezone semantics must be explicit.

### Decision 4

Temporal relationships should be generated from business constraints rather than independent random timestamps.

### Decision 5

Lifecycle and status are conceptually different.

### Decision 6

Temporal behavior should reuse the common distribution and reproducibility architecture.

### Decision 7

Focused temporal strategies are preferred over a generic TemporalManager.

### Decision 8

The current compact schemas should not be expanded implicitly merely to support future temporal features.

### Decision 9

Seasonality and campaigns should be modeled as reusable temporal context.

### Decision 10

Customer lifecycle should eventually influence activity and purchasing behavior.

### Decision 11

Temporal skew should be available as both realistic business behavior and explicit benchmark scenarios.

### Decision 12

Temporal validation belongs in the validation architecture rather than being scattered across generators.

### Decision 13

Parallel generation must preserve logical temporal correctness and reproducibility.

### Decision 14

Temporal characteristics should contribute to dataset observability and identity.

### Decision 15

The generator should remain Spark-independent while producing data suitable for Spark temporal workloads.

# 107. Final Design Summary

The target temporal architecture is:

```text
                    Dataset Clock
                         |
              +----------+----------+
              |                     |
          Calendar              Time Window
              |                     |
       +------+------+              |
       |             |              |
  Seasonality    Campaigns          |
       |             |              |
       +------+------+-+------------+
              |
       Temporal Context
              |
      +-------+--------+
      |                |
Customer Lifecycle   Product Lifecycle
      |                |
      +-------+--------+
              |
       Customer Behavior
              |
       +------+------+
       |             |
    Sessions       Orders
       |             |
     Events       Payment
                      |
                   Shipment
                      |
                   Delivery
                      |
                    Return
```

The central idea is:

> **Time should describe the causal evolution of the ShopSphere business world, not decorate independently generated records with random timestamps.**

A realistic dataset should allow a downstream analyst to ask:

```text
What happened before the order?
How long did the customer browse?
Did the campaign increase demand?
Which customers became more active?
How did shipment delays change during demand spikes?
Which products became popular during a season?
How long after delivery were products returned?
```

and receive answers that make business sense.

This temporal coherence is essential for the later Spark Performance Laboratory because realistic event-time distributions, lifecycle behavior, and temporal skew directly affect joins, windows, aggregations, partitioning, and event-time processing.

The architecture should therefore treat temporal modeling as a domain capability spanning the entire synthetic business world, while keeping generic time arithmetic, probability distributions, randomness, and storage concerns in their appropriate cross-cutting layers.
